# Spike S-C — bare-ffmpeg / bare-media for the L8 transcode lane

Date: 2026-09-04 · Runtime under test: Bare 1.31.0 (v8 14.8, uv 1.52.1) and Node v22.22.0 · Host: laptop2 (linux-x64, i5-1235U, no sudo, **no system ffmpeg/ffprobe**) · Scratch: `/tmp/opencode/spikes/S-C`

## Question

What do `bare-ffmpeg@1.5.0` and `bare-media@2.10.5` actually expose for (a) probing, (b) transcoding to a 1080p/720p/360p **H.264 MP4 + faststart** ladder, (c) thumbnails at timestamps, (d) storyboard sprites? Is `bare-subprocess@6.1.0` + system ffmpeg a workable fallback? Does any of it run under plain Node so `@sovit/core/media` can stay runtime-agnostic?

## Method

`npm install --ignore-scripts bare-ffmpeg@1.5.0 bare-media@2.10.5 bare-subprocess@6.1.0 bare` (60 pkgs, 726 MB). Read vendored READMEs, then the real `index.js`/`lib/*`/`src/*`/`binding.cc`/`CMakeLists.txt`, `package.json`, `prebuilds/`. Ran 5 scripts under the prebuilt `bare` binary: export listing + encoder/decoder/muxer probing; synthetic-clip encoding (mpeg4/VP9 into MP4/WebM via custom write IO, seekable and non-seekable, `faststart`, `h264_vaapi`); probe/thumbnail/storyboard/transcode via bare-media; bare-subprocess spawn tests. Then tried the same `require`s under Node 22. No upstream test files ship in the npm tarball; patterns were taken from `bare-media/src/video/transcoder.js`.

## Findings

1. **Install under `--ignore-scripts` is complete — no build step exists.** `bare-ffmpeg` and `bare-subprocess` have `"addon": true` and ship `prebuilds/<platform>/<name>.bare` for 13 targets (android-arm/arm64/ia32/x64, darwin-arm64/x64, ios-arm64/-simulator, ios-x64-simulator, linux-arm64/x64, win32-arm64/x64). No `node-gyp-build`, no `install` script; build is `cmake-bare`/`bare-make` (dev-only). `npm rebuild` is neither needed nor possible without a toolchain. `bare-ffmpeg/prebuilds/linux-x64/bare-ffmpeg.bare` = **40.4 MB** (statically linked FFmpeg + bundled `libva.so.2`/`libva-drm.so.2`; whole package 400 MB on disk across all platforms — prune per-platform when packaging). `bare-subprocess` linux-x64 = 16.7 KB. `bare` pulled `bare-runtime-linux-x64@1.31.0` (`bin/bare`, 95.9 MB) but its mode landed **0664** and npm created **no `.bin/bare` link** (both `bare` and `bare-runtime-linux-x64` declare `bin: bare`; the conflict is silently skipped). `npx bare` → "not found"; `node node_modules/bare/bin/bare` or `chmod +x` the runtime binary works.

2. **bare-ffmpeg exports (from `index.js`, verified live):** `AudioFIFO ChannelLayout Codec CodecContext CodecParameters Decoder Dictionary Encoder Filter FilterContext FilterGraph FilterInOut Frame HWDeviceContext HWFramesContext HWFramesConstraints IOContext Image InputFormat InputFormatContext OutputFormat OutputFormatContext Packet Samples Scaler Stream Rational Resampler log constants`. Key signatures: `new IOContext(bufferOrSize, {onread(buf,n), onwrite(buf), onseek(off,whence)})`; `new InputFormatContext(io | InputFormat, options?, url?)` → `.streams .duration(µs) .readFrame(pkt) .getBestStream(type) .getBestStreamIndex .getStream .dump .inputFormat`; `new OutputFormatContext(nameOrFormat, io)` → `.createStream() .writeHeader(dict?) .writeFrame(pkt) .writeTrailer()`; `new Encoder(name|codec)` / `new Decoder(name|codec)`; `new CodecContext(encoderOrDecoder)` → get/set `width height pixelFormat sampleFormat sampleRate timeBase frameRate channelLayout gopSize flags extraData hwDeviceCtx getFormat`, `open(dict?) sendFrame receivePacket sendPacket receiveFrame setOption getOption listOptionNames getSupportedConfig`; `Stream` → `index codec codecParameters sideData timeBase avgFramerate duration decoder() encoder()`; `Scaler(srcFmt,w,h,dstFmt,w,h).scale(src,dst)`; `Image(fmt,w,h).fill(frame)/.read(frame)/.data`; `FilterGraph.parse/configure/pushFrame/pullFrame`; `Packet.rescaleTimestamps(src,dst)`; `Dictionary.from(obj)`. Everything is synchronous and blocking on the main thread.

3. **NO `seek` anywhere.** `binding.cc` contains no `av_seek_frame`/`avformat_seek_file` (only `seek_preroll` getters). The only "seek" is the *IO* callback. Thumbnails at a timestamp therefore mean **linear decode from byte 0** to the target frame (bare-media's `extractFrames({frameIndex})` does exactly this: `src/video.js:23-66`). Measured: frame 45 of a 1080p mpeg4 clip = 60 ms; 5 storyboard frames = 214 ms (5 × full re-open + decode). Cost scales O(position) per thumbnail — fine for short clips, bad for hour-long uploads unless we decode once and harvest all thumbnails in one pass (feasible with the raw API; not with bare-media's helper).

4. **NO software H.264 encoder in the prebuild.** `CMakeLists.txt`: `ffmpeg_features = dav1d svt-av1 opus vpx`, `BARE_FFMPEG_ENABLE_GPL=OFF` by default (x264 is GPL; upstream will not ship it). Live `new Encoder(name)` probe: **present** `h264_vaapi libvpx libvpx-vp9 libsvtav1 libopus aac mpeg4 mjpeg rawvideo flv h263 pcm_s16le`; **absent** `libx264 libopenh264 h264 h264_v4l2m2m libx265 hevc libaom-av1 png libmp3lame`. Decoders present: `h264 hevc vp9 av1 aac opus mp3 mpeg4 prores`. Muxers present: `mp4 mov webm matroska image2 mjpeg hls mpegts`. So bare-ffmpeg can *read* anything users upload but can only *write* VP9/AV1/mpeg4-ASP video. **The H.264 ladder requirement cannot be met by bare-ffmpeg in software.** `h264_vaapi` exists and `HWDeviceContext(VAAPI)` initialised on this laptop (`iHD_drv_video.so`, `/dev/dri/renderD128`), but the encode failed `EIO` on my first attempt (frame upload path — likely my usage, not proven either way); it is hardware-dependent and useless on a VPS without a GPU.

5. **`movflags=faststart` is impossible through bare-ffmpeg.** `openOutputFormatContext` calls `avformat_alloc_output_context2(..., NULL, NULL)` (binding.cc:562) — no URL — and movenc's faststart pass re-opens `s->url` for reading. Result: `writeTrailer()` throws **`No such file or directory`** with both a non-seekable and a fully seekable custom `IOContext` (tested; output left as `ftyp free mdat` with **no moov at all** = corrupt file). What works: plain MP4 with a seekable sink (`ftyp free mdat moov`, moov last) and fragmented MP4 `frag_keyframe+empty_moov` (`ftyp moov moof mdat…`, moov first — streams fine, but is fMP4, not "faststart"). A JS moov-relocation post-pass (qt-faststart algorithm, ~150 lines: move `moov` before `mdat`, patch `stco`/`co64` offsets) would close the gap for whatever bare-ffmpeg *can* encode.

6. **bare-media is a thin, opinionated layer; `mp4` means VP9+Opus.** `src/video/transcoder.js` `formatRegistry`: `webm|mp4|matroska|mkv` all = `libvpx-vp9` (YUV420P, `deadline=realtime cpu-used=6 crf=34 b=0`, gop 30) + `libopus` 48 kHz; the mp4 muxer opts are `frag_keyframe+delay_moov+default_base_moof`. `video(path).transcode({format,width,height})` is an async generator yielding chunks (verified 1080p→360p: 520 ms, 4 chunks, 30.9 KB). No codec, bitrate, or CRF options are exposed; it is marked experimental. `video(path).metadata()` (verified, ~3–23 ms) returns `{width,height,codec:{id,name},duration(s),avgFramerate:{numerator,denominator},displayRotation,rotation,flipH,flipV}` for the best **video** stream only and throws if none — no audio streams, bitrate, or container info; use the raw `InputFormatContext.streams` for a full probe (verified: `inputFormat.name`, per-stream codec/w/h/timeBase/duration/fps/bitRate). `extractFrames({frameIndex})` returns `{width,height,data:RGBA}` for **one** frame index (not a timestamp). `image.resize/encode` (bare-jpeg/bare-png/bare-webp) + a JS blit produced a real 800×90 JPEG storyboard (11.9 KB) and 320×180 thumbnail (7.6 KB). All image helpers are `async` (returned Promise, not a buffer — bit me once). bare-media is ESM-only with extensionless relative imports (`export * from './src/codecs'`).

7. **bare-ffmpeg encoding itself works and is fast enough for a synthetic test:** mpeg4 320×240 60 f = 32–84 ms; mpeg4 1080p 60 f = 628 ms; VP9 720p 60 f (realtime/cpu-used 8) = 377 ms; VP9 320×240 = 40 ms. Output written through `IOContext.onwrite` to a `bare-fs` fd; WebM and plain MP4 **require** an `onseek` callback (2 seeks on trailer) or fail `Function not implemented` (ENOSYS).

8. **Under Node 22: nothing bare-* native loads.** `require('bare-ffmpeg')` → `TypeError: require.addon is not a function` (binding.js is literally `module.exports = require.addon()`); same for `bare-subprocess`. `require('bare-media')` → `ERR_MODULE_NOT_FOUND … /src/codecs` (extensionless ESM import). Even with a `require.addon` shim it cannot work: the `.bare` has **41 undefined `js_*`/`uv_*`/`bare_*` symbols** resolved by the Bare binary (which exports 261 `js_*` functions); Node exports only N-API (`process.versions.napi=10`). Bare-modules doc line 179 confirms the two addon ABIs are distinct (`bare-compat-napi` goes the *other* direction: N-API addons on Bare). There is no Node build of bare-ffmpeg.

9. **bare-subprocess is a fully workable `child_process` analogue on Bare.** Exports `Subprocess ChildProcess(alias) constants errors spawn spawnSync`; `spawn(file, args?, {cwd,stdio,shell,detached,uid,gid,env,serialization})` with `stdin/stdout/stderr` as `bare-pipe` streams, `exit/close/error/message` events, `kill(sig)`, IPC via `stdio:'ipc'`; `spawnSync` returns `{status,signal,stdout,stderr,output,error?}`. Verified: `spawnSync('sh',…)` status 3 + stdout captured; async `spawn` streamed 100 KB and exited 0. **Node-compat difference:** `spawn()` of a missing binary **throws synchronously** (`Error: no such file or directory, code: ENOENT`) instead of emitting `'error'`; an uncaught throw aborted the Bare process (core dump). Wrap in try/catch. `engines.bare >= 1.7.0`.

10. **No system ffmpeg on this host**, so the subprocess+ffmpeg path could only be verified as "spawn works", not end-to-end. On the gateway/VPS a static ffmpeg binary (or apt) would be a deployment dependency — outside this spike.

## Decision

- **L8 transcode lane: `bare-subprocess` (Bare) / `child_process` (Node) + an external `ffmpeg` binary.** bare-ffmpeg cannot produce H.264 (no x264, GPL-off by upstream policy), cannot write faststart MP4, and cannot seek — three of the four hard requirements. Keep bare-ffmpeg/bare-media **only** for what they do well today: fast **probe** (`video().metadata()` or raw `InputFormatContext`), single-pass thumbnail/storyboard harvesting on short clips, and an optional VP9/AV1 rendition (`libvpx-vp9`, `libsvtav1` are present and could later replace H.264 if the player policy changes).
- **`@sovit/core/media` stays runtime-agnostic by design, not by shared binaries:** define the media *plan* (ffprobe-style JSON → ladder spec → argv for `ffmpeg`, moov-first check, sprite geometry, VTT for storyboards) in pure JS with an injected `spawn(file,args,opts)` + `fs` adapter. Provide two tiny adapters: `node:child_process` for the gateway and `bare-subprocess` for Pear/Bare workers. Codec-in-process paths (bare-ffmpeg probe/thumbnails) go into a **Bare-only optional package** (`@sovit/media-bare` or similar) loaded lazily via `import()` and guarded, because the addon is a 40 MB per-platform `.bare` that cannot load in Node at all.
- Do **not** plan on `h264_vaapi` for servers; treat it as an unproven desktop-only optimisation.

## Open questions

1. Is a shipped/static `ffmpeg` acceptable in the Pear desktop bundle (size, GPL licensing of x264 in a distributed app) — or does desktop-side transcoding move to the gateway entirely? If the player can accept **VP9/AV1 MP4/WebM** instead of H.264, bare-ffmpeg becomes viable and the ffmpeg binary dependency disappears on desktop (a JS faststart post-pass would still be needed for non-fragmented MP4).
2. Does upstream plan to add seek (`av_seek_frame`) to bare-ffmpeg? Without it, timestamp thumbnails on long videos are O(n) decodes; the single-pass harvest workaround should be prototyped and timed on a ≥30 min H.264 file.
3. `h264_vaapi` returned `EIO` — real driver/frame-upload problem or my `HWFramesContext`/`transferData` usage? Only worth chasing if desktop hardware encode is ever a requirement.
4. Which `ffmpeg` binary + version pinning/checksum strategy for the gateway (apt vs static build), and where does S-C's probe JSON contract get reconciled with `ffprobe -print_format json` output so both probe paths yield one schema?
5. Packaging: `bare-ffmpeg` is 400 MB on disk across 13 prebuild targets; confirm Pear's bundler prunes non-target `prebuilds/` and that the bundled `libva*.so.2` sidecar directory survives packing on linux.
