## What was built

`@sovit/seeder` — the daemon of build-plan §2.1: Corestore + Hyperblobs, swarm join per
core, `pay/1` server side hooks, swap/nutzap batching, sha256 CAS index, disk cap,
per-pubkey rate limits + global stream cap, persisted ban list, melt command, systemd
hooks, redacting logger. Everything integrates against `mocks.MockPaymentEngine` /
`mocks.MockWallet` from `@sovit/core`; the real engine (Stage 2) drops in behind the same
`PaymentEngineSeeder` interface.

## Runtime verification of spike S-A (finding 3) — numbers

Test: `src/__tests__/replication.integration.test.ts` ("S-A finding 3"), two `Seeder`
instances over directly piped `replicate()` streams, 20-block fixture blob, 1 KiB blocks:

| `windowBlocks` | `upload` events at the seeder | viewer blocks after the cut | engine window |
|---|---|---|---|
| 4 (default) | 5 | **4** | uploaded 5, paid 0, outstanding 5, banned |
| 2 | 3 | **2** | uploaded 3, outstanding 3, banned |
| 7 | 8 | **7** | uploaded 8, outstanding 8, banned |

So: `upload` fires before the block hits the wire, `recordUpload` is called inside the
handler with no `await`, `outstanding > windowBlocks` on the crossing block triggers
`banList.ban` + `engine.ban` + `peerInfo.ban(true)` + `stream.destroy()` in the same tick,
and the viewer holds **exactly `windowBlocks`** blocks. Confirmed 5/5 repeated runs.

Same scenario over real hyperswarm on a local `hyperdht` testnet
(`src/__tests__/swarm.integration.test.ts`): the seeder-side accounting is identical
(exactly window+1 recorded, cut on the crossing block, PeerInfo banned, no reconnection
accepted before or after a restart) but the viewer ends with **≤ window** blocks — observed
3 of 4 in most runs, 4 in some. Two transport facts explain it, both worth knowing:

1. `stream.destroy()` on a UDX socket drops bytes already handed to the transport but not
   yet flushed, so a block Hypercore *did* send can still be lost. Money-wise this is in
   the seeder's favour (residual loss ≤ window, never more).
2. After `destroy()`, Hypercore's `_handleRequests` loop can still pop one more queued
   request before the peer is marked `removed` (that happens on the async `close`), so a
   6th `upload` event may fire for window 4. Its `wireData.send` goes to a destroyed
   stream and is a no-op; the seeder's gate ignores post-cut events, so the engine still
   records exactly window+1. The direct-pipe rig never showed this; the wire rig does
   intermittently. The swarm test therefore asserts `raw upload events ≥ window+1`,
   `session/engine uploaded == window+1`, `0 < viewer blocks ≤ window`.

## Assumptions and decisions (please read)

- **Pre-`HELLO` identity.** Hypercore starts serving as soon as the replication channel
  opens; `pay/1`'s `HELLO` (which binds the Nostr pubkey) races it. `PeerSession` accounts
  blocks uploaded before the bind against the **Noise key hex used as the `NostrPubkey`
  string** (same 32-byte hex shape) and, on `bindPubkey()`, replays that count with one
  `recordUpload(pubkey, n)` so the engine's window for the real pubkey is correct
  (`n ≤ window`, so the replay can never itself cut). A viewer that never sends `HELLO`
  is cut after `windowBlocks` like any other non-payer. The engine keeps a stale
  provisional window entry for that Noise hex; harmless, visible in `windows()`.
  If Stage 2 prefers, a `rebind(from, to)` on the engine would remove the replay — not
  requested now, the replay is contract-clean.
- **`PayMessage` carries no core key.** The contract's range is "within one core", but a
  Corestore connection replicates many cores over one `pay/1` channel. The seeder verifies
  every `PAY` against one `PricePolicy` per seeder (`config.policy` / `setPolicy()`), i.e.
  one price for everything this node seeds — matching HELLO's per-seeder `satsPerBlock`.
  Per-video prices need either a core key in `PAY`/`HELLO` or one `pay/1` channel per
  core. Flagging for Wave 2 / Stage 2; not blocking.
- **Ban-list precedence.** `PeerSession.cut('window-exceeded' | 'banned')` writes the
  Noise key to the ban list if it is not there yet, reusing an existing pubkey ban's
  reason; `Seeder.ban()` (operator) writes first, so its reason wins. Other cut reasons
  (`local`, `remote`, `protocol-error`) drop the connection without banning.
- **Two synchronous cut paths.** `PeerSession.onUpload` cuts on the returned window, AND
  the seeder subscribes `engine.onWindowExceeded` and cuts every session for that pubkey.
  `MockPaymentEngine` fires the callback *inside* `recordUpload`, so the callback path
  usually lands first; `cut()` is idempotent. Both are in the `upload` tick.
- **Disk cap counts payload bytes** (what the CAS index stores), not on-disk bytes
  (Hypercore tree/bitfield/RocksDB overhead is excluded). Size the cap a few percent under
  the real budget. The cap is rebuilt from the index on start.
- **Put = hash pass then write pass** for files/streams (two reads), so a duplicate is
  never written and the cap is checked before any block lands. Chunking to `blockSize`
  is done by the seeder because `Hyperblobs.createWriteStream()` makes one block per
  `write()` (verified in `hyperblobs/lib/streams.js`).
- **Hyperblobs `end` is inclusive** in range reads; `createBlobReadStream` keeps that.
- **`Corestore.replicate(bool)` mints a fresh Noise keypair per stream.** A client that
  wants its bans to stick must pass its stable key pair: `seeder.replicate(false, { keyPair })`.
  Tests use `DHT.keyPair(seed)`. Over hyperswarm the swarm's key pair is used, as expected.
- **Half-open piped pairs.** With `a.replicate(true)` piped to `b.replicate(false)`, only
  the destroying side's Noise stream reliably emits `close`; the other end can sit
  half-open. Tests wait on the seeder's stream. Real transports close both ends.
- **`MemoryDenyWriteExecute` is OFF** in the unit. §7 asked to test it against the JIT:
  `systemd-run --user -p MemoryDenyWriteExecute=yes node -e …` on Node 22.22.0 aborts V8
  (`Check failed: 12 == errno`, ENOMEM on the JIT mapping); `node --jitless` works.
  Operators may add both at a throughput cost. Every other §7 directive is in
  `HARDENING_DIRECTIVES` and asserted by test.
- **`sd_notify`** goes through the `systemd-notify` binary (`Type=notify`,
  `NotifyAccess=all`) because Node's `dgram` cannot speak `AF_UNIX` and native modules
  are off-limits. No-op without `NOTIFY_SOCKET`.
- **No self-executing daemon `main()`** and no `bin/`: a real `PaymentEngineSeeder` does
  not exist until Stage 2, and root-level `eslint .` type-checks stray `.mjs` files I
  cannot add to its config. The shell that owns the engine (L6 worker, or a service
  entry) calls `runDaemon({ config: parseDaemonEnv(proc).config, deps, proc, logger })`.
  The reference unit's `ExecStart` points at that shell-supplied entry. Likewise `melt` is
  `runMelt(argv, { wallet, logger })`; wire it to a `bin` once a `Wallet` exists.
- **Bare.** Plain ESM, no top-level Node APIs outside `adapters/node/`. `setTimeout`,
  `TextDecoder`, `queueMicrotask`, `Uint8Array` only. The `.d.ts` imports
  `node:events` types only (Bare's `bare-events` is shape-compatible).
- **Deps:** none added at runtime. `hyperdht@6.34.0` added as a **devDependency** of
  `packages/seeder` (already in the lockfile at that exact version; installed with
  `npm install --ignore-scripts --offline`). Used for `hyperdht/testnet.js` and
  `DHT.keyPair` in tests only.

## Things I was unsure about

- Whether L3/L6 want the seeder to own the `PayProtocol` instance. I chose not to: the
  seeder exposes `attachPayProtocol(session, protocol)` and depends only on the contract
  interface, so Stage 2's implementation (locked dir) can be attached by whoever
  constructs it with the mux. If the orchestrator prefers the seeder to construct it,
  that is a 10-line change in `Seeder.onSwarmSession`.
- `RateLimiter` keys on the Noise key at admission; the per-*pubkey* dimension is
  enforced indirectly (a pubkey's sessions are all Noise-keyed; bans cover both). A
  second `admit`-style check keyed on the Nostr pubkey at `bindPubkey` time is trivial to
  add if wanted.
- `PeerSession.info().window` reads `engine.window(accountId())` — for a closed session
  this is a snapshot at call time, which is what the events carry.

## v3 re-issue (2026-09-05)

Branch `lane/L2-v3`, based on `main @ f780abb`, against `CONTRACTS_VERSION = 3`
(`docs/decisions/0004-contracts-v3.md`). Scope = `docs/lanes/L3.md` "What the seeder's v3
re-issue must change for me", items 1–7, nothing else. No contract change requested
(`docs/contract-requests/L2-v3.md` does not exist on purpose). Still integrates against
`mocks.MockPaymentEngine('honest')`; nothing here implements hashing, signatures, blinding
or key derivation.

### What changed, per item

1. **`PeerSession.onUpload` → `engine.recordUpload(accountId(), 1, coreKeyHex)`.** The
   core the `upload` event came from is forwarded (cast to `CoreKeyHex`; the registry's
   gate passes `toHex(core.key)`). The engine now keeps per-core counts, so the mock's
   per-core `range-not-uploaded` fires for the gateway's downstream viewers. The session
   also records the set of cores it has uploaded from (`uploadedCores`, see item 3). The
   window stays per peer summed over cores (ADR 0004 (c)); the synchronous cut path is
   untouched — same tick, no `await`.
2. **`bindPubkey` → `engine.rebind(noiseKeyHex, pubkey)`** replaces `recordUpload(pubkey,
   replay)`. `pubkeyBound` is set BEFORE the call so that, if the merge crosses the window
   and the engine fires `onWindowExceeded` synchronously, the seeder's belt-and-braces
   subscription already finds this session by pubkey and cuts it inside `rebind`. The
   session additionally checks the returned window (`outstanding > windowBlocks` →
   `window-exceeded`; a carried-over ban → `banned`) for an engine without listeners.
   Binding the same pubkey twice does not call `rebind` again (no double count). The
   provisional counter is kept only for the `pubkey bound` log line (`provisionalBlocks`).
   Verified (test b): after `bindPubkey`, `engine.windows()` has NO Noise-hex entry and the
   pubkey's window carries the pre-`HELLO` blocks with their per-core breakdown (a PAY
   naming that core for those blocks verifies).
3. **Core-less `PAY` on a multi-core stream → `ACK{ok:false, reason:'malformed'}`** in the
   pay bridge, before the engine sees it, and without cutting (a refusal, not a ban). "The
   stream replicates > 1 core" is `max(replicatedCores(), session.uploadedCores.size)`
   where `replicatedCores` is what `Seeder.attachPayProtocol` supplies: the number of open
   cores with a Hypercore replication peer on this session's stream (`core.peers`, matched
   by `peer.stream === session.stream` or the remote Noise key). That counts a core the
   peer has attached to but not yet pulled from — the integration test asserts the
   refusal with only ONE core uploaded from so far. With one core the v2 aggregate
   semantics still apply, so a v2 client keeps working against a single-video seeder until
   the Stage 2 bump makes `core` required.
4. **Policy resolved per `range.core`.** `PayBridgeOptions.policy` is now
   `(core?: CoreKeyHex) => PricePolicy` (a v2 `() => PricePolicy` still type-checks and
   ignores the core). `Seeder.setPolicy()` / `policy()` stay the DEFAULT; new
   `setCorePolicy(core, policy | null)`, `policyFor(core?)` and `corePolicyMap()` give the
   gateway's per-core upstream policies a downstream counterpart. `setCorePolicy` announces
   no `PRICE`: the v2 `PRICE` carries no core, so it cannot express a per-core change
   (noted by L3 too; a Stage 2 codec matter). Verified (test c): a PAY for core B is
   verified against B's policy — B's blocks paid at the default price / default creator are
   refused (`wrong-p2pk-target` first, `wrong-amount` with the right creator), paid under
   B's policy they are accepted; core A without an override uses the default.
5. **`BlobStore.putStream` opens the second `source()` lazily.** `writeHashed` now takes an
   `open` thunk called once, inside the `try`, immediately before the write pass; the
   dedupe and disk-cap early returns never open it. Verified (test d) with a source that
   throws ENOENT on its second open (dedupe path and cap path both return normally, the
   factory was called once) and with the exact shape L3 hit — `putFile` on an
   already-stored file, `unlink` right after the result, wait — which produced an uncaught
   ENOENT against the v2 code (confirmed by running the new test against it).
6. **`PeerSession.mux`** getter (additive): the `Protomux` Hypercore put on the Noise
   stream (`noiseStream.userData`), structurally checked against the contract's `MuxLike`,
   `null` on a stream without one. The gateway can attach `pay/1` with `session.mux`
   instead of reaching through `noiseStream.userData`. Verified in the two-core integration
   test (`session.mux === sa.noiseStream.userData`). `userData` was added to the seeder's
   ambient `ReplicationStream` type as optional. Not added to the `session-open` payload:
   `PeerSessionInfo` is a plain snapshot and stays that way.
7. **Decision: the renderer is DELETED.** `renderSystemdUnit()`, `HARDENING_DIRECTIVES`,
   `SystemdUnitOptions`, the duplicate `packages/seeder/systemd/nutflix-seeder.service`,
   its byte-match test (`systemd-file.test.ts`) and the directive test in `systemd.test.ts`
   are gone. Reasoning: the canonical `deploy/systemd/nutflix-seeder.service` (L9, tested,
   read-only for this lane) is a commented operator file whose facts (`Type=simple`,
   `MemoryDenyWriteExecute=yes` + `node --jitless`, `AF_NETLINK`, `StateDirectory`,
   `NODE_OPTIONS=` pin, resource caps) all contradicted the v2 renderer; a function that
   emits that file byte-for-byte is a string constant pretending to be a renderer, and the
   moment L9 touches the file it drifts again — exactly what L3 concluded for the gateway.
   `sdNotify()` and `installShutdownHooks()` stay (the gateway's `cli/main.ts` uses both;
   `sdNotify` is a no-op without `NOTIFY_SOCKET`, harmless under `Type=simple`). The
   `host/systemd.ts` module comment now points at `deploy/systemd/` as the single source of
   truth. This is the one REMOVAL from the v2 "Public API" block — sanctioned by item 7 and
   consumed by nobody (grep: only the seeder's own tests and docs referenced it).

### Things I was unsure about

- `replicatedCores` compares `peer.stream === session.stream` and falls back to the remote
  Noise key. Both hold for `Seeder.replicate()` and swarm connections (the session stream
  IS the Noise stream that `protomux.stream` points at); the key fallback covers any
  wrapper a future transport might introduce. If a peer has attached to a core but the
  seeder has it closed, it is not counted.
- `setCorePolicy` is a plain map keyed by `CoreKeyHex`, not a resolver callback. A
  callback form (`setPolicyResolver`) is a five-line addition if the gateway prefers to
  derive downstream policy from its upstream map on the fly rather than mirror it.
- The canonical unit's `ExecStart` runs `packages/seeder/dist/index.js --config
  /etc/nutflix/seeder.json`; `@sovit/seeder` still has no self-executing `main()` (v2
  decision, not in items 1–7). Flagging, not changing — L9's README lists it as the one
  line this lane must confirm, and the gateway's `cli/main.ts` is the pattern to copy when
  a `PaymentEngineSeeder` exists.
- One run of the pre-existing `S-A finding 3 … windowBlocks=7` case hit vitest's 5 s
  default once during development (normally 1.7 s; 6 subsequent full-suite runs clean,
  also clean on `main`). Load-related; left as is.
