## Assumptions

1. **Split rounding**: `seeder = floor(total × seeder% / 100)`, creator gets the remainder. Taken
   from the reference model's `pay()`/`verify()`; SECURITY.md only says "split per the video's
   `split` tag". INV2 pins this rule because `pay` and `verify` must agree on it.
2. **Kind 24242 rules**: the vendored `docs/vendor/BUD-01.md` is the newer revision that moved
   the authorization-event definition out (to BUD-11, not vendored). The suite encodes the rules
   every Blossom server implements and the contract's `reason` enum mirrors: `Nostr <base64
   JSON>` header, kind 24242, `created_at` in the past, required future `expiration`, `t` = verb,
   `x` = blob hashes, valid signature. BUD-04 mirror reuses the `upload` token (BUD-04 "Example
   Flow" step 3).
3. **`allow()` lifts a `deny()`**; the suite does not assume an exclusive allow-list.
4. Where the spec leaves the reason genuinely ambiguous (missing `expiration`, missing `t`, missing
   `x`, future `created_at`, id-mismatch after tampering) the test asserts rejection with 401 and
   the reason **in a two-element set**; every other case asserts the single specific reason.
5. **Codec round-trip uses `toStrictEqual`**: optional fields absent on input must be absent on
   output (contracts compile with `exactOptionalPropertyTypes`). A decoder that emits
   `reason: undefined` fails on purpose.
6. `nostr-tools` is imported from `packages/gateway` although only `@sovit/core` declares it; it
   resolves through the hoisted workspace `node_modules` (verified at runtime and under `tsc -b`).
   **Recommendation for L3/orchestrator**: add `nostr-tools` as a gateway devDependency so the
   resolution is declared, not incidental. I cannot edit `package.json`.

## Observations about the mock vs SECURITY.md (reported, not "fixed")

1. **P2PK check is envelope-only.** `verify()` compares `LockedProofSet.lockedTo` to the expected
   key; it never parses the NUT-11 secret. A captured set with `lockedTo` re-labelled to the
   thief's key is **accepted** by the mock. Covered by the Stage-2-only `T6 … re-labelled` test.
2. **`C` is never checked** (DLEQ stand-in is `dleq.s !== FORGED`). Covered by the Stage-2-only
   `T7 … C is altered` test.
3. **Small-amount rounding makes honest PAYs unpayable.** With `satsPerBlock: 1`, one block at
   50/50 yields seeder share `floor(0.5) = 0` → `denominate(0) = []` → the honest PAY is rejected
   as `missing-seeder-set`. Every fixture video with price 1 sat hits this for single-block PAYs.
   Not a SECURITY.md contradiction (INV2 says exact), but a spec gap: either the viewer must batch
   until both shares are ≥ 1 sat, or the split needs a stated minimum-batch/rounding rule. The
   property tests filter to scenarios where both shares are ≥ 1 (≥ 2 for the mode sweep so
   `underpay` stays distinguishable from an empty set). Suggest the orchestrator decide and, if
   needed, add it to `PricePolicy` docs — no contract shape change required.
4. A rejected cheat (`forge`, `overpay`, …) does not ban in the mock; only window-exceeded and
   double-spend do. SECURITY.md mandates bans only for T3/T5, so the suite leaves this open
   (asserts only "never credited").
5. `verify` returns `peer-banned` before `malformed` for banned peers; ordering is not pinned.

### What the mock cannot express (item 5, and one clause of item 3)

Verified empirically before writing a single assertion (probe run, then deleted):

1. **"Stream replicates > 1 core ⇒ core-less PAY is `malformed`" — not expressible.**
   `MockPaymentEngineOptions` has no core set, `PaymentEngineConfig` has no core set, and
   `verifySync` falls back to the v2 aggregate count when `range.core === undefined`
   (`mock-payment-engine.ts:254-255`) — **even after uploads were recorded on two distinct cores
   for that peer**. A core-less `[0,3]` against a peer with 4×A + 4×B recorded is **accepted**
   (`ok: true, credited: 8`). The seed suite pins the single-core version of that fallback
   (`a v2-shaped PAY without core still verifies against the aggregate count`), so the mock is
   behaving as documented, not as the contract's multi-core rule. What is pinned instead: the
   normative sentence in `contracts/payment.ts` and ADR 0004 (c) (regex, comment-line-break
   tolerant), `core` shape validation → `malformed`, and a full-bodied `it.skipIf(usingMock())`
   test that asserts `malformed` once ≥ 2 distinct cores have recorded uploads for the peer.
   Caveat in its title: the ADR says *the seeder* rejects, so if Stage 2 puts the check in the
   pay-protocol seeder rather than the engine, move that test to `pay-protocol/__tests__/`.
   The mock's acceptance is also pinned in `mocks/__tests__` under an explicit
   `DOCUMENTED v3-INTERIM FALLBACKS` title so the day the mock changes, the change is noticed.
2. **"Per-core `range-not-uploaded` fires when the PAY names a core with no uploads" — not
   expressible.** The per-core check engages only for a core that **has** an entry in
   `uploadedByCore` (`perCore ?? w.uploaded`); naming a core with none falls back to the
   aggregate. With 4×A recorded, a PAY for `CORE_NONE[0,0]` is **accepted** (`ok: true,
   blocks: 1`). This matches the ADR's wording ("whenever the PAY names a core for which uploads
   were recorded"), so it is an interim rule, not a mock bug. The per-core property in
   `INV1 per core` therefore quantifies only over cores with a count and says so in a comment;
   the Stage 2 expectation is the full-bodied skipped `INV1 per core (v3): a PAY naming a core
   with NO recorded uploads is range-not-uploaded …` — sound at v4 because `core` becomes
   required on `recordUpload`, so "no record" means "never sent".

Neither gap needs a contract change; both are closed by the Stage 2 bump the ADR already
schedules. **No entry in `docs/contract-requests/L10-v3.md`; the file is intentionally not created.**
